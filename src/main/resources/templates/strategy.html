Overview

The bot trades NIFTY weekly options on the Indian market, using Camarilla pivots derived from the previous day's high, low, and close to identify high-probability reversal and breakout levels. Every trade is a premium-selling position — the bot sells out-of-the-money (OTM) calls or puts depending on the directional bias of the setup, profiting from time decay and the underlying staying within an expected range.

Entries are gated by a strict two-candle confirmation + trigger model on 5-minute NIFTY spot bars, plus an RSI-14 momentum band filter that ensures the broader spot momentum agrees with the setup's thesis. Risk management is built in at three layers: per-trade R:R floor, per-day budget cap, and a daily squareoff time.

Camarilla Pivots

Computed nightly from the previous day's High, Low, and Close. The pivot range k = 1.1 × (H − L) sets the scale of all levels:

H5(H ÷ L) × C — extreme upside
H4C + k/2 — breakout level
H3C + k/4 — upper reversal zone
PP(H + L + C) ÷ 3 — pivot point
L3C − k/4 — lower reversal zone
L4C − k/2 — breakdown level
L5(L ÷ H) × C — extreme downside

The L3–H3 band is the "neutral" core; price spending time inside it tends to mean-revert. The H4 / L4 levels mark the structural edges — a sustained break beyond them signals a directional regime change. H5 / L5 are extreme-move targets, reached only on strong-trend days.

The Four Setups

All setups go SHORT an OTM option. Bullish bets sell PUTs (profit if NIFTY stays above the put's strike); bearish bets sell CALLs (profit if NIFTY stays below the call's strike). The bot picks the OTM leg at session-start and holds the same four symbols all day.

Two-Candle Entry Model

Every 5-minute bar close on NIFTY spot runs a four-phase walk. A bar must FIRST seed a pending confirmation, then a SUBSEQUENT bar must trigger it before the trade fires. The two-bar gate filters out single-bar noise: roughly 60% of confirmations fail to trigger and get dropped without trading.

Phase 1
Trigger — if a pending exists AND the current bar fires through the confirmation extreme in the same direction, place the SELL order. Bullish trigger = green bar, close > confirmation high. Bearish = red bar, close < confirmation low.
Phase 2
Expiry — a pending older than 6 bars (30 min) is dropped without trading. The confirmation went stale; the move it predicted didn't materialize.
Phase 3
Invalidate — if the current bar's close moves AGAINST the pending's wicked extreme, the thesis is broken and the pending is dropped immediately.
Phase 4
Detect — if nothing fired/expired this bar, check whether the CURRENT bar's geometry matches any setup's confirmation pattern (wicked through a level AND closed back across it). If yes, seed a new pending. Bar color does NOT matter at confirmation — the trigger candle's color filter handles direction.

RSI Momentum Gate

At trigger time, before the SELL order goes out, the bot checks NIFTY RSI(14) against a setup-specific band. The momentum check filters out late-entry breakouts at exhaustion (RSI > 80) and reversals against a strong trend (RSI < 40 for bullish reversals, > 60 for bearish reversals).

H4_BREAKOUT60 < RSI < 80
L4_BREAKDOWN20 < RSI < 40
L3_REVERSAL40 < RSI < 60
H3_REVERSAL40 < RSI < 60

Breakouts require directional momentum WITH the trade (RSI in the 60-80 / 20-40 band — trending but not exhausted). Reversals require neutral momentum (RSI 40-60 — no strong trend in either direction, since a rejection thesis can't hold against a runaway move). The check uses the live LTP-projected RSI at the instant of trigger; the chart visible on the Positions page streams that same value every second via SSE.

The momentum gate can be toggled OFF in Settings → Camarilla pane. When disabled, all setups fire on geometry + trigger alone, regardless of RSI.

Order Flow & Exit Logic

When a trigger fires and all gates pass, the bot places a single SELL order on the pre-resolved OTM option leg for that setup. Position size = lots-per-leg × NIFTY lot size (default 1 lot × 65 contracts). No SL or target orders are placed on the option premium directly — both are monitored against the NIFTY spot futures and the bot exits via a market order when either threshold is crossed.

  • Target — spot reaches the setup's Camarilla target level (H3 / L3 / H5 / L5). Position closes with profit; theta + favorable spot move both contribute.
  • Stop loss — spot crosses the confirmation candle's far extreme (plus a configurable buffer in points, default 5). Position closes with loss; the spot moved against the thesis.
  • 3-tick SL confirmation — to avoid wick-driven false exits, the SL only fires after 3 consecutive sub-second polls confirm the level is breached.
  • Timed squareoff — at the configured squareoff time (default 15:15 IST), all open positions are flattened regardless of SL/target state.

Risk Management

  • Per-trade R:R floor — every fire computes reward (entry → target) and risk (entry → SL). If R:R < 1:1, the trade is rejected. Toggleable in Settings → Risk pane.
  • Per-day exposed-risk cap — running total of projected losses across all open positions is checked against portfolioMaxDailyRisk. If exceeded, the session is force-locked and all open positions are flattened.
  • Concurrent position cap — at most N simultaneous bot-managed positions (default 4).
  • Trading window — new entries only fire between configured Trading Start (09:30 IST default) and Trading End (13:30 IST default). Existing positions continue to be managed until squareoff.

Real-Time Monitoring

The bot maintains two persistent Fyers WebSocket connections during market hours: one for market data (NIFTY spot + every subscribed option leg's LTP and OI) and one for order events (entry fills, modifications, cancellations). Sub-second SL/target checks run on every spot tick — no polling latency between a level breach and the exit order going out.

Three browser-side surfaces stream live state via Server-Sent Events: the navbar ticker (NIFTY LTP + ΔPct), the Positions page (per-position LTP + MTM), and the Momentum (RSI) chart (live LTP-projected RSI + last-closed canonical RSI, refreshed ~1 Hz). All persistent state survives mid-day restarts and weekend gaps via JSON disk snapshots.
